# citation-check 공급 준비 초안 (적용 전, 사용자 승인·서명 필요)

서비스: `citation-check` (Cotejo Citation Check, 50,000 CUPR, 체인 공급자 0). 소유자는 NFT KING 쪽이고 우리가 공급자로만 붙는다.

## 알아낸 것
1. 릴레이마이너 `config.main.relayer.yaml`은 서비스마다 `backends.rest.url` 하나만 받고, 요청에 인증 헤더를 넣는 항목이 없다. 상대 백엔드가 토큰 헤더를 요구하면 우리 릴레이마이너가 직접 부를 수 없다.
2. 해결 후보 (새 비용 없음): 맥에 이미 있는 `rpc_normalizer.py`와 같은 방식의 작은 로컬 중계기(예: 127.0.0.1:88xx)를 두고, 그 중계기가 상대 백엔드로 보낼 때 헤더를 붙인다. 토큰은 맥의 환경변수나 권한 600 파일에만 두고 저장소·기억·채팅에는 남기지 않는다. 릴레이마이너는 그 로컬 주소만 본다.
3. 체인 쪽: 공급자 서비스 갱신(`stake-supplier --services-only`)은 서비스 목록 전체를 다시 쓴다. 기존 서비스를 빼먹으면 빠진다. 그래서 현재 목록을 읽어 `citation-check` 한 항목만 더한 파일을 만들어야 한다. 서명은 사용자.
4. 지금 체인에서 `citation-check` 공급자는 0이다.

## 순서 (각 단계 앞에 사용자 승인)
1. 상대에게 백엔드 정식 주소와 "헤더 이름·토큰"을 보안 경로로 받는다(이미 DM에서 받은 값 사용 가능, 이후 교체 권고).
2. 로컬 중계기 작성·시험(읽기 전용 호출 `GET /health`), 맥 launchd 등록.
3. `config.main.relayer.yaml`에 `citation-check` 항목 추가, `relayer validate` 통과 시에만 재시작(실패 시 백업 복구).
4. 현재 공급자 서비스 목록 + `citation-check`로 스테이크 갱신 파일 작성 → 사용자 서명. 가스만 든다.
5. 다음 세션부터 릴레이가 들어오는지 확인.

## 위험
- 상대 백엔드가 다운되면 우리 릴레이가 5xx를 낸다(공급자 점수 -25/건). 상대와 가용성 합의 필요.
- 물량이 아직 없어 수익은 사실상 0에 가깝다. 목적은 생태계 협력이다.
- 다른 서비스 공급 목록을 빼먹는 실수가 가장 큰 사고 경로다(3번).
